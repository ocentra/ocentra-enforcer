## Where We Are

Common/security rules often run raw text over every family, while language-specific rules duplicate related intent. Neither route declares a closed fact capability.

## Where We Want To Be

A generic rule names its normalized facts/tool results and runs only where those capabilities are proved. Per-language fixtures establish semantic equivalence; missing capability is visible rather than regex fallback by accident.

## Owns

- one predicate implementation/family, exact metadata, disjoint fixtures, and immutable registry proposal;
- no new facts, language onboarding, framework profile, shared registry, graph provider, or external runner.

## Objective

Reuse one reliable mechanical predicate across languages while preserving language-specific evidence and honest limits.

## Requirement Checklist

- [ ] Predicate statement is language-neutral and mechanically decidable.
- [ ] Required capabilities are closed and already proved for each target row.
- [ ] Each target language has positive/negative/malformed/unavailable fixtures.
- [ ] Severity, message, spans, and ordering are deterministic.
- [ ] T2 threshold/false-positive evidence exists when exact T1 is impossible.
- [ ] Ineligible recognized languages receive a coverage diagnostic or not-applicable disposition, not clean.
- [ ] Reuse assessment confirms an existing mature engine does not already own the predicate better.

## Acceptance And Proof

Run rule registry/fixture parity, per-language dispatch matrix, unavailable behavior, selected scan/MCP surfaces, cargo gates, and scoped Enforcer checks. Manager reproduces one case per target language.

## Stop conditions

Stop when a target lacks required capabilities, the predicate becomes ecosystem-specific, or implementation needs new fact/tool/graph/shared-registry work.

## Parallel Ownership Notes

Fixture preparation can parallelize by target language. Predicate and registry integration remain single-writer.
