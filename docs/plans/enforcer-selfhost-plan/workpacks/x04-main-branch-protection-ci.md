## Where We Are
This repo does NOT protect `main` today (owner directive 2026-07-04; AUDIT_FINDINGS.md WAVE 5). CI exists (`.github/workflows/ocentra-enforcer.yml`, and c10 builds the release/bootstrap pipeline), but nothing REQUIRES CI to be green before a merge lands on `main`, and nothing prevents a force-push, an admin override, or a "merge when red" from putting an unvalidated tree onto the trunk. The enforcer's whole doctrine is "only green, proven trees advance" — yet the trunk of the enforcer's OWN repo is presently unprotected: a direct push or a red-CI merge can land on `main` with zero mechanical resistance. There is no emitter that CONFIGURES GitHub branch protection for `main`, and no verifier that ASSERTS the protection is actually in place and non-bypassable. Two adjacent audit rows confirm the gap and its scope: RELEASE_POLICY's "release-cut-from-green-`main`" gate (c10 territory) presumes a protected `main` that does not yet exist, and the legacy `BRANCH_PROTECTION.md` names required GitHub contexts that are stale pre-rename and were never actually applied as settings. The OcentraParent clone that carried the canonical `.github/workflows` branch-protection pattern is gone, so the pattern here is authored from the standard GitHub required-status-checks + no-bypass shape and must be reconciled against OcentraParent's ACTUAL workflow/job names at build time.

## Where We Want To Be
A Rust emitter/verifier — `crates/enforcer-install/src/ci/branch_protection.rs` — that (a) EMITS the desired protection configuration for `main` (required status checks = the enforcer CI job(s); require PRs; block force-push; disallow admin/override bypass of required checks) and applies it via `gh api` (GitHub branch-protection REST) or an equivalent config surface, and (b) VERIFIES the live protection matches the desired state and ASSERTS it is present and non-bypassable, failing closed if it is missing or bypassable. `main` is protected such that: no merge lands unless the required enforcer CI job(s) are green; required checks cannot be bypassed (no force-push to `main`, no admin override of the required checks, no "merge when red"); this ties into the `pr_ready` flow so only a green `main` is merge-eligible. The desired settings are documented in this repo's own `.github/BRANCH_PROTECTION.md` (the settings-as-doc source of truth the emitter applies and the verifier checks against). The required-check contexts are declared symbolically and RECONCILED against OcentraParent's actual workflow/job names at build time — never hardcoded to a stale context string. One documented, distinct exception exists: an emergency `--no-verify`-class push escape that SAVES STATE (a save-state / snapshot push to a non-`main` ref) and explicitly does NOT merge to `main` — it is a break-glass state-preservation path, categorically separate from the merge gate, and it never satisfies or bypasses the required-status-checks that guard `main`.

## Requirement Checklist
- [ ] Required-status-checks configured for `main`: the enforcer CI job(s) (the check contexts emitted by `.github/workflows/ocentra-enforcer.yml` / c10's pipeline) are declared REQUIRED for merge. Contexts are declared symbolically and reconciled against OcentraParent's actual workflow/job names at build time — no stale/hardcoded context string. **Fail fixture:** `main` with no required checks (or a check not marked required) -> verifier check fails. **Pass fixture:** `main` with the enforcer CI job(s) marked required -> verifier passes.
- [ ] "No bypass / no force-push / no admin-override of required checks": force-push to `main` is blocked, admin override of the required checks is disallowed, and there is no bypass allowance that would let a merge skip the required checks. **Fail fixture:** protection present but bypassable (admins can override, or force-push allowed) -> check fails. **Pass fixture:** protection present AND non-bypassable -> check passes.
- [ ] PRs cannot merge red: a PR whose required enforcer CI job(s) are failing/pending is NOT merge-eligible (require-branches-up-to-date + required checks passing before merge). **Fail fixture:** a red/pending required check that is nonetheless merge-eligible -> check fails. **Pass fixture:** red required check correctly blocks merge -> check passes.
- [ ] Verifier ASSERTS the protection is in place (fail-closed): the verifier reads the live branch-protection state (`gh api`/config) and asserts it matches the desired `.github/BRANCH_PROTECTION.md`. **Fail fixture:** protection missing OR bypassable -> verifier exits non-zero. **Pass fixture:** protection present, required, and non-bypassable -> verifier exits zero.
- [ ] Ties to the `pr_ready` flow: only a green `main` is merge-eligible; the verifier is a gate the `pr_ready`/merge flow consults, so a merge cannot proceed against an unprotected or red `main`.
- [ ] Emergency `--no-verify` push escape documented as a DISTINCT exception: a break-glass save-state / snapshot push to a NON-`main` ref that preserves work in progress and explicitly does NOT merge to `main` and does NOT satisfy or bypass the required-status-checks guarding `main`. Documented in `.github/BRANCH_PROTECTION.md` as the ONLY sanctioned escape, and it never lands on the protected trunk.
- [ ] Clean `cargo clippy` / `cargo fmt --check`. Obey `[workspace.lints]` (no `unwrap`/`expect`/`panic`/`print_*` outside the sanctioned sink); no `pub use` barrels.
