## Where We Are
The multi-agent coordination hub is JS today, in THREE layers that all live under `src/coordination/`:
1. **Vendored engine** `src/coordination/vendor/*.js` (domain, paths, root, events, identity, claim-policy, lock-policy, lock-policy-singletons, stream, materialize, materialize-claim-identity, presence, health-presence, guard, doctor, repair, server, daemon, cli, notify, peers, retention, read-index, manifest, dashboard, context).
2. **Public API surface** `src/coordination/api.mjs` (~983 lines) — the command-level orchestration: `claim`/`release`/`status`/`health`/`inbox`/`closeout`/`compact`/`index`/`repair`/`presence`/`peer`/`sync`, editIntent/onConflict handling, closeout scoped-release filters, stale-session/claim detection. **Previously omitted from this pack — it is load-bearing.**
3. **Runner / CLI dispatch** `src/coordination/runner.mjs` (~798 lines) — the "org chart" engine: lifecycle-report structured-field validation, session-lease claim/release (TTL), thread-mode-state, delegate-grant/revoke (coordinated-delegate vs read-only), hook-context injection. **Previously omitted from this pack — it is load-bearing.**

None of it is Rust and none of it is a workspace crate. The port must cover all three layers, not just `vendor/*.js`.

## Where We Want To Be
`enforcer-coordination` is the Rust coordination engine per RUST_ARCHITECTURE.md: hub/lane/claim/guard/ledger/presence/sync built on `enforcer-domain` (`HubName`, `LaneId`), porting the entire `src/coordination/vendor/*.js` tree PLUS `api.mjs` (public command surface) and `runner.mjs` (session-lease / thread-mode / delegate / lifecycle-report engine) to Rust. This is the crate that MUST port `src/coordination/{vendor/*.js,api.mjs,runner.mjs}` -> Rust with behavior parity.

- [ ] Port `src/coordination/vendor/*.js` to Rust in `crates/enforcer-coordination` per RUST_ARCHITECTURE.md — explicitly: this crate ports `src/coordination/vendor/*.js` -> Rust.
- [ ] Cover the subsystems: hub, lane, claim + claim-policy, guard, ledger/events + materialize/read-index, presence + health-presence, sync + stream, plus identity, lock-policy, repair, retention, peers, notify, manifest, dashboard, context, root/paths.
- [ ] **Preserve the multi-machine/multi-project semantics exactly** (see EXECUTION_MODEL.md §2c — verified against the vendored `.js` source, not new scope): `presence` groups rows `byPc`/`byProject`/`byWorktree`/`byLane`/`byThread` with heartbeat-expiry + stale/offline detection; `peers` is a named registry (name, URL, `pull`/`push`/`both` mode, optional token-env); `sync` (http + local transports) pulls a peer's event-stream manifest, appends ONLY new lines (never rewrites), and on divergence writes a `<stream>.conflict.<ts>` file rather than silently merging. This is what makes the hub a genuinely distributed, cross-machine, cross-project coordination plane — it must not regress to single-machine/single-project during the port.
- [ ] **Preserve `pr_ready` as a first-class gated state + the `"primary"` lane's special status** (EXECUTION_MODEL.md §2d): `WorkerState`/`TaskState` include `pr_ready`; the `pr_ready` operation is guarded on `allowMergeRisks`; a literally-named `"primary"` lane carries `allowPrimaryWithoutClaims`. Only the primary lane's workflow is meant to open a PR — worker lanes transition to `pr_ready` + mail, they never open a PR themselves. This is a protocol invariant, not incidental behavior — do not drop it while porting.
- [ ] **Decide + document the claim-conflict scoping** (EXECUTION_MODEL.md §2d — VERIFIED GAP: today's `detectConflicts()` keys claims by bare normalized relative path, no `worktreeRoot`): either (i) keep one-hub-per-worktree/lane as the operational convention (default, matches current usage), or (ii) key claim conflicts by `(worktreeRoot, normalizedRelPath)` if a workpack needs one shared hub across many worktrees. Pick one explicitly in the Rust port; do not silently inherit the ambiguity.
- [ ] **Lane-worktree spawn primitive (product capability, not just our own bootstrap trick — see EXECUTION_MODEL.md §1.3/§2b):** `enforcer coordination lane new <lane-id> [--branch <name>] [--worktree-path <path>]` — creates a fresh `git worktree` for the lane (defaults to a sibling directory named after the lane), runs hub `init` for it, and returns `{lane, hub, worktreeRoot, branch}` as JSON. Contract is TOTAL ISOLATION by construction: it never points at or shares another lane's `target/`/`node_modules`/build cache; each spawned worktree is a bare git checkout only — installing/building toolchain state is the calling agent's job. Also exposed as an MCP tool (consumed by arc-21) so any harness (Claude Code, Cursor, Codex, Windsurf, ...) driving parallel workers gets this pattern without hand-rolling `git worktree` calls.
- [ ] `enforcer coordination lane park <lane-id>` / `lane rm <lane-id> [--clean]` — park leaves the worktree + its build artifacts on disk indefinitely (no-op, cheap); `rm --clean` deletes the worktree (and prunes it from git) as a normal, zero-drama operation, never a failure path.
- [ ] Build all coordination identifiers/records on `enforcer-domain` newtypes (`HubName`, `LaneId`, etc.); parse-at-boundary for the on-disk ledger/index.

### Load-bearing semantics — per-mechanic provable rows (from AUDIT_FINDINGS WAVE 2 arc-16)
Each row names its home module, the exact source it ports, and the fail/pass fixture that proves it. Ported from `src/coordination/vendor/lock-policy{,-singletons}.js`, `events.js`, `guard.js`, `repair.js`, `retention.js`, `stream.js`, `read-index.js`, `notify.js`, `server.js`, `daemon.js`, `api.mjs`, `runner.mjs`.

- [ ] **Lock-kind taxonomy + the 6 conflict classes** (`src/lock/**` <- `vendor/lock-policy.js`). Port the 4 lock kinds `{writeLock, globalWriteLock, branchLease, workReservation}` (rejection on unknown kind, per `normalizeLockKind`) and `classifyClaimPair`'s 6 conflict classes: `write-lock-conflict`, `branch-write-conflict`, `global-write-conflict`, `branch-lease-conflict`, `merge-risk`, `work-reservation-overlap`, with the exact key-derivation (`physicalKeys` = project:worktree:path, `globalKeys` = project:group, `branchKeys` = project:branch[:path]) and the ownership dimensions (project via projectId/gitRemote/repoRoot, worktree, branch, logical owner via codexThreadId/codexSessionId).
  - Fail fixture: two claims by different owners on the same normalized path in the same worktree -> `write-lock-conflict` in `hardConflicts`. Pass fixture: same two claims in *different* worktrees on *different* branches -> only a `merge-risk` advisory, no hard conflict. Additional pass: two `workReservation` claims on the same-branch overlapping path -> `work-reservation-overlap` advisory only (never a blocker).
- [ ] **Protected-singleton auto-escalation to `globalWriteLock`** (`src/lock/**` <- `vendor/lock-policy-singletons.js` + `enrichClaim`). Any path matching a protected-singleton group — lockfiles (`Cargo.lock`/`package-lock.json`/`pnpm-lock.yaml`/`yarn.lock`/`uv.lock`/`poetry.lock`), release files (`CHANGELOG`/`VERSION`/release-notes), `**/migrations/**`, `**/generated/**` (+ generated schema/contract/dto/bridge), and `.github/workflows/**` — is force-escalated to `globalWriteLock` regardless of the declared kind, keyed by `project:group` (cross-worktree). This is the ONE intentional cross-worktree lock. **Reconcile with EXECUTION_MODEL §2d: add this as the completing clause — §2d today documents claim scoping but omits the singleton escalation; the port must make §2d and this row agree (the primary-lane / one-hub convention holds for ordinary writeLocks; protected singletons deliberately break worktree isolation).**
  - Fail fixture: two lanes in *different* worktrees both claim `Cargo.lock` -> `global-write-conflict` (proves cross-worktree escalation). Pass fixture: those same two lanes claim two distinct ordinary source files in different worktrees -> no conflict.
- [ ] **editIntent / onConflict=intent / release->notify wait-notify overlap protocol** (`src/api.rs` + `src/events/**` <- `api.mjs:242-271`). `onConflict` normalizes to `{fail, intent}`; when `intent` and a blocker exists, append an `editIntent` event (`intentFor: "writeLock"`, `intentQueued: true`) instead of failing; on release of the blocking claim, `notify`/`inbox` surfaces the queued intent to its waiter. (Consumed by b04.)
  - Fail fixture: `onConflict=fail` against a held conflicting claim -> claim rejected. Pass fixture: `onConflict=intent` against the same held claim -> no error, an `editIntent` event is appended and appears in the blocked owner's queue; releasing the holder makes the intent claimable.
- [ ] **Session-lease + thread-mode + delegate-grant "org chart" engine** (`src/session/**` <- `runner.mjs:365-537`). Port `session.claim`/`session.release` with `ttlSeconds` (default 7200) and active-session tracking (`active-session.json`); `thread-mode-state.json` (latestUserPromptSessionId + mode `default`|`manual-only`); `hub:delegate:grant`/`revoke` writing `delegateGrants`; and the three-way write-gate resolution in hook-context: lease-holder (writable), coordinated-delegate-grant (writable without the lease), else read-only.
  - Fail fixture: a second session issues an edit-gated op while another session holds the lane lease and has no delegate grant -> resolves READ-ONLY. Pass fixtures: (a) lease holder resolves writable; (b) after `delegate grant` for the second session, it resolves COORDINATED-DELEGATE-GRANT writable; (c) after TTL expiry the lease is reclaimable.
- [ ] **Lifecycle-report structured-field validation** (`src/runner.rs` <- `runner.mjs:327-363`). A report whose first line matches `STARTED|BLOCKED|PR_READY|DONE` MUST carry a `--details` block with the base fields `{lane, threadId, assignedBy, plan, workpack, worktree, branch, scope}` plus state-specific fields: STARTED->`startedAt`, BLOCKED->`blocker`, PR_READY->`validation`, DONE->`validation,commit`. Missing fields throw with the exact missing-field list. This is the mechanical due-diligence gate behind §2d `pr_ready`.
  - Fail fixture: `PR_READY` report with no `validation` field -> rejected naming the missing field. Pass fixture: `DONE` report with all base fields + `validation` + `commit` -> accepted.
- [ ] **Guard operation modes + focused-vs-global findings + truncation budget** (`src/api.rs`/`src/events/**` <- `vendor/guard.js`). Operations `{inspect, edit, commit, push, rebase, merge, pr_ready}`; guard runs `inspectLedger`, produces `focused` findings (scoped to `changedPaths`) vs `globalWarnings` (bounded by `limit`, with `globalWarningsTruncated`/`globalWarningCount`); `inspect` never blocks; non-inspect on a non-primary lane with unread messages adds a finding; only `pr_ready`+`primary` captures the full global set today (preserve that budget).
  - Fail fixture: `commit` guard over a corrupt ledger -> finding emitted, non-zero gate. Pass fixture: `inspect` over the same corrupt ledger -> findings reported but never blocks; and a healthy ledger `commit` -> clean.
- [ ] **Wire-hash vs extension-hash canonicalization + golden sentinel** (`src/events/**` <- `vendor/events.js:97-150`). Port the exact `WIRE_HASH_FIELDS` allow-set (id, schema, hub, nodeId, nodeName, lane, writer, type, ts, seq, prevEventId, prevHash, to, body, messageId, paths, reason, owner, owners, state, workerState, taskId, taskState, title, prUrl, summary, ttlSeconds, sessionId), the canonicalization ordering, and the property that `context` (projectId/repoRoot/etc.) is EXCLUDED from the wire hash. A Rust port that diverges makes every existing ledger fail hash checks and breaks cross-impl sync.
  - Golden fixture: hashing `HASH_COMPATIBILITY_SAMPLE_EVENT` MUST equal `EXPECTED_HASH_COMPATIBILITY_WIRE_HASH = sha256:c4333184613bd63a0d2918e3be4c88ce2ea4a32d9fc7e07bb755ade688aada76`. Fail fixture: mutating a `context` field must NOT change the hash; mutating any wire field MUST change it.
- [ ] **Repair = 3 distinct engines** (`src/repair/**` <- `vendor/repair.js` + `api.mjs`). (1) legacy-hash reconcile (`repairLegacyHashCompatibility` — rewrite old-scheme hashes to wire-hash), (2) sequence-break rehash (`repairSequenceBreaks` — repair `seq`/`prevHash` chains), (3) stale-claim / claim-conflict resolve (release expired/stale claims and resolve conflicts, driven from the api-level repair op). Preserve write vs dry-run gating.
  - Fail fixture (dry-run): repair reports the 3 defect classes without mutating the ledger. Pass fixture (apply): after repair the ledger passes guard/hash checks; a stale claim past TTL is released.
- [ ] **Closeout scoped-release + stale-claim repair filters** (`src/api.rs` <- `api.mjs:812-834`, `closeoutFilters`/`matchingCloseoutClaims`). Closeout releases only claims matching the requested scope filters: `lane` (unless includeAllLanes), `writer`, `nodeId` (writer prefix), `thread`/`session`, `projectId`, `worktreeRoot` (resolved path). 
  - Fail fixture: closeout scoped to lane A must NOT release lane B's claims. Pass fixture: closeout scoped to a nodeId releases exactly that node's claims across its lanes.
- [ ] **Retention / compact -> archived-segment model** (`src/sync/**` (or `src/retention` submodule) <- `vendor/retention.js` + `vendor/stream.js:82-108`). `compactLedger` moves old events to `archived/<stream>/<stamp>.ndjson`; `streamSegments` reads archive segments + the live stream as one logical stream (archived-first ordering).   - Fail fixture: after compaction a full `readAllStreams` must still return every original event in order. Pass fixture: compaction produces an `archived/<stream>/<stamp>.ndjson` file and the live stream shrinks.
- [ ] **Read-index + OPT-IN SQLite hot index** (`src/sync/**` (or `src/index` submodule) <- `vendor/read-index.js`). Always write the JSON view `db/coordination-index.json` (+ `coordination-index-status.json`); the SQLite hot index (`db/coordination.sqlite`) is OPT-IN via `OCENTRA_COORDINATION_SQLITE=1`. **Port decision: SQLite is OPT-IN, JSON is the default cross-platform fallback** (do not port `node:sqlite` as a hard dep; gate it behind a cargo feature `sqlite-index` + the same env var, so JSON-only remains the default and CI needs no native SQLite).

### Intra-pack disjoint module sub-units (this crate is too big for one worker)
This pack is deliberately larger than one worker should own. Split it INTO the crate by module sub-unit; multiple workers can claim these concurrently because the module trees are disjoint. The coordination hub's OWN claim mechanism scopes them (each sub-unit owner claims its subtree; the crate root `Cargo.toml` + `src/lib.rs` are a protected-singleton-style shared file, claimed briefly for module wiring only). Declared sub-units and their source-of-truth JS:

- `src/domain.rs` / re-exports on `enforcer-domain` — identity, paths, root, manifest (`vendor/{domain,identity,paths,root,manifest}.js`). Foundational; land first.
- `src/lock/**` — lock-kind taxonomy, 6 conflict classes, protected-singleton escalation, claim-policy (`vendor/{lock-policy,lock-policy-singletons,claim-policy}.js`).
- `src/session/**` — session-lease TTL, thread-mode-state, delegate-grant engine (`runner.mjs:365-537`).
- `src/sync/**` — stream append-only, materialize, retention/compact archive segments, read-index (JSON + opt-in SQLite), peers + sync transports, (feature-gated) serve/daemon (`vendor/{stream,materialize,materialize-claim-identity,retention,read-index,peers,server,daemon}.js`).
- `src/repair/**` — the 3 repair engines + doctor/inspectLedger (`vendor/{repair,doctor}.js`).
- `src/events/**` — event schema, wire-hash canonicalization + golden sentinel, guard operation modes, presence/health-presence, notify (`vendor/{events,guard,presence,health-presence,notify}.js`).
- `src/api.rs` — public command surface: claim/release/status/health/inbox/closeout/compact/index/repair/presence/peer/sync, editIntent/onConflict, closeout scope filters (`api.mjs`).
- `src/runner.rs` — CLI dispatch + lifecycle-report structured-field validation + hook-context injection (`runner.mjs`, non-session parts).

Claim/dependency order for concurrent workers: `domain` -> (`lock`, `events`, `sync` in parallel) -> (`session`, `repair`) -> (`api`, `runner`). Workers coordinate through the hub's claim tool on these exact subtrees; only `Cargo.toml`/`src/lib.rs` require a short shared (globalWriteLock-style) claim.
