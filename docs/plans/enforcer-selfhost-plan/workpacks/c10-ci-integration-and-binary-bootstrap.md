## Where We Are
Proof is never uploaded between our own swarm lanes (EXECUTION_MODEL.md §2b/§2c) — but that is an INTERNAL build-isolation rule, and it is a different question from how a DOWNSTREAM CONSUMER PROJECT'S CI regenerates proof for itself. Today (verified against this repo): (1) `docs/TARGET_REPO_WIRING.md` describes the CURRENT `.mjs` model — target repos "call the installed enforcer with an explicit root" rather than vendoring source (already an improvement over the original copy-`.mjs`-into-every-project era) — but its "Codex Runtime Flow" hardcodes `E:/ocentra-enforcer/rules/INDEX.md`, a LOCAL absolute path that cannot resolve on any machine but the original author's, and certainly not on a cloud CI runner. This is a real bug independent of the Rust pivot. (2) This repo's OWN CI (`.github/workflows/ocentra-enforcer.yml`) installs a full Node toolchain AND a full Rust toolchain (`rustup toolchain install ...`) just to run `npm ci && npm run ci:local` — fine for the enforcer's OWN dogfood CI (it needs the toolchain to build/test itself regardless), but NOT an acceptable ask of every consumer project's CI once the engine is a compiled Rust binary — no consumer should need to install Rust to run a linter. (3) There is no reusable GitHub Action, install script, or npm-wrapper package for consumers today.

## Where We Want To Be
Any consumer project's CI (GitHub Actions, GitLab CI, CircleCI, Bitbucket, Jenkins, or bare shell) can run the `enforcer` binary WITHOUT installing a Rust toolchain, by one of: (a) a portable `install.sh`/`install.ps1` script (curl/iwr-installable) that detects OS/arch, downloads the matching release binary from GitHub Releases, verifies its checksum, and installs it to a bin dir — the universal, CI-provider-agnostic path; (b) a reusable composite GitHub Action (`.github/actions/enforcer-scan`, wired by the `github-actions` install adapter) that wraps (a) plus caches the downloaded binary (keyed by version+platform) via `actions/cache`, for GitHub users specifically; (c) an OPTIONAL npm wrapper package (a thin JS shim + per-platform `optionalDependencies`, the same pattern biome/esbuild/swc use) so any consumer ALREADY wired the old Node-centric way (`npm install` + `npx enforcer ...`, per the current `TARGET_REPO_WIRING.md`) keeps working with ZERO wiring changes even though the underlying package now ships a compiled binary. `cargo install` from source remains a documented FALLBACK for platforms without a prebuilt asset, never the primary path. Every one of these paths RUNS THE BINARY FRESH against the CI checkout every time — CI never trusts or reuses a pre-computed/uploaded proof artifact (extends the swarm's own zero-trust/no-upload doctrine to the consumer-CI boundary); CI MAY separately choose to upload its OWN freshly-generated report as a build artifact for human PR review afterward — a legitimate, different act from trusting an upload as a shortcut, and must not be confused with it. The `E:/ocentra-enforcer` hardcoded-path bug is fixed: rules are compiled into the binary (arc-04's rules-as-data) and reachable via `enforcer explain <ruleId>`, never a bare hardcoded filesystem path.

## Requirement Checklist
- [ ] Adopt `cargo-dist` (or an equivalent hand-built pipeline matching its shape) to generate the GitHub release workflow (plan -> build -> host -> publish across the win/mac/linux + musl + apple-silicon matrix already declared in RUST_ARCHITECTURE.md's Distribution section) and the portable `install.sh` (POSIX, detects `uname -s`/`uname -m`, handles glibc vs musl on Linux) + `install.ps1` (Windows) installer scripts, checksum-verified. This IS the enforcer's own repo CI's job — it builds and PUBLISHES the release; every consumer project's CI merely POINTS AT it (per owner directive: "ci of this repo will make distro and binaries for all platform and keep as release; other projects' CI point to that release").
- [ ] Build+release BOTH the `full` and `ci`/`lite` binary variants (per arc-22's Cargo feature split) as distinct assets per platform; the installer script/GH Action/npm-wrapper DEFAULT to the `lite` variant for CI use (no coordination hub, no UI needed in a headless mechanical CI run) with an explicit opt-in to `full` if a consumer genuinely wants it.
- [ ] **Pre-publish cross-platform smoke gate — a release is never published broken.** Before any GitHub Release goes live, run the built binary (both variants, every target platform) through a minimal fail/pass smoke fixture in CI; a broken/panicking binary on ANY platform blocks the release entirely. Rationale (owner directive): a consumer's CI is FULLY MECHANICAL with no Codex/Claude present to notice something is off — "that cannot be because of fucked up enforce." The enforcer's own reliability bar is categorically higher once it sits on other projects' CI critical path.
- [ ] **Version-pinning guidance, not blind "latest."** Document (and make the installer default to) a PINNED version reference recorded in the consumer's own repo (e.g. a lockfile-style version stamp the `github-actions`/generic adapter writes), with an explicit opt-in "floating latest" channel for teams that want it. Rationale: unlike our own swarm (where a human reviews changes), a rule change in a blindly-"latest"-pinned enforcer could silently break many unrelated consumer CIs with zero warning — pin-by-default avoids this while still allowing "latest" as a deliberate choice.
- [ ] **CI-runner platform coverage is independent of what platform the TARGET project itself builds for.** The win/mac/linux(+musl+arm) matrix already covers every real CI runner family; a project targeting mobile/embedded/etc. still runs its CI on an ordinary x86/arm mac/linux/windows runner — we do NOT cross-compile the enforcer itself to run on a phone. Document this explicitly so it is never mistaken for a missing platform-support gap.
- [ ] Build the reusable composite GitHub Action at `.github/actions/enforcer-scan/**`: detects `runner.os`/`runner.arch`, checks an `actions/cache` entry keyed by `enforcer-version+platform` before downloading, installs via the script from the previous bullet if not cached, then exposes the binary on `PATH` for the calling workflow's own `run: enforcer scan ...` step (or optionally runs the scan itself with typed inputs/outputs). Wired into target repos by the existing `github-actions` install adapter (already referenced in `TARGET_REPO_WIRING.md`'s adapter list).
- [ ] Build the OPTIONAL npm wrapper package (`packages/enforcer-cli/` or similar): a thin JS shim `package.json` with per-platform `optionalDependencies` (`enforcer-cli-linux-x64`, `enforcer-cli-darwin-arm64`, etc., each just bundling the matching release binary) so `npm install` + `npx enforcer ...` keeps working for consumers already wired that way, with npm's platform resolution picking the right binary automatically (glibc/musl runtime-detected on Linux per the Orhun-blog/cargo-npm pattern).
- [ ] Fix the `E:/ocentra-enforcer` hardcoded-path bug: no doc, adapter, or generated CI config may ever reference a literal local absolute path. Replace `TARGET_REPO_WIRING.md`'s "Read E:/ocentra-enforcer/rules/INDEX.md" step with `enforcer explain <ruleId>` (rules are compiled into the binary via arc-04's rules-as-data, no external file to locate). Coordinate with x02 (docs-refresh) which owns this file's prose; this pack owns fixing the underlying MECHANISM the doc describes.
- [ ] Doctrine enforcement: CI always regenerates proof fresh (never reads/trusts a pre-computed or uploaded artifact as a substitute for running the binary); document the distinct, legitimate separate act of a CI job uploading its OWN freshly-generated report as a build artifact for human review.
- [ ] `cargo test -p enforcer-install` (or a dedicated integration test) proves: the installer script fixture correctly resolves each of the declared OS/arch combinations to the right release-asset name (both `full` and `lite` variants); a corrupted/checksum-mismatched download is rejected (fail-closed, no silent fallback); the GitHub Action fixture asserts cache-hit skips re-download and cache-miss downloads+caches; the default fetched variant for CI use is `lite`; no fixture or generated config contains a literal absolute local path; a seeded internal-error-class exit code from the binary is surfaced distinctly from a rule-violation exit code in the installer/action's own reporting.
- [ ] Clean `cargo clippy` / `cargo fmt --check`.
