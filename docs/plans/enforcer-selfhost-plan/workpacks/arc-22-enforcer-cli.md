## Where We Are
CLI entrypoints belonged to the retired Node engine (script entrypoints + output family). That engine is dropped; there is no single Rust binary that is both the CLI and the MCP stdio server.

## Where We Want To Be
`enforcer-cli` is the clap CLI per RUST_ARCHITECTURE.md that compiles to the `enforcer` binary (one binary IS the engine) and is a FIRST-CLASS product surface — equally first-class with the MCP, not secondary: `enforcer scan|check|install|serve|plan|proof|...`, and when invoked as an MCP server it serves `enforcer-mcp` on stdio. This is the single distributed artifact. It stands up the crate SKELETON with the tri-modal scope grammar, exit-code-driven verdicts, terse `Fix:` hints, NO override flag, and Windows-first argv handling; the `print_stdout`/`print_stderr` deny-wall lints are allowed in exactly ONE output-sink module. It hosts the d06 lifecycle-command family (`src/lifecycle.rs`).

## Requirement Checklist
- [ ] Implement the clap CLI per RUST_ARCHITECTURE.md with the subcommands (`scan`, `check`, `install`, `serve`, `plan`, `proof`, ...), each wired to the corresponding engine crate.
- [ ] Define the tri-modal scope grammar in clap: `enforcer check <paths...>` | `--base <sha> --head <sha>` | `--all` (mutually-exclusive scope selection), exit-code-driven (non-zero on findings), Windows-first (argv-quoting + backslash path normalization).
- [ ] Emit terse `Fix:` hints per finding when rendering a `Report`; there is NO override/bypass flag — the enforcer cannot be silenced from the command line; the ONLY exemption is a declarative, committed, gated waiver read from `enforcer-config`.
- [ ] Confine all stdout/stderr writes to ONE output-sink module carrying a scoped, documented `#![allow(clippy::print_stdout, clippy::print_stderr)]`; every other module obeys the `[workspace.lints]` deny wall. This is the ONLY sanctioned print site in the crate.
- [ ] **`lite`/`full` Cargo feature split, ONE source tree (DRY — no forked/duplicate CI-only crate)** (owner directive, 2026-07-04): `enforcer-cli` gains a `full` feature (default) pulling in `enforcer-coordination` (arc-16) + `enforcer-ui` (arc-24), and a `ci`/`lite` profile (`--no-default-features --features lite` or equivalent) that EXCLUDES both from the dependency graph and disables their subcommands (`coordination *`, `serve`/`ui`) entirely at compile time — a genuinely smaller/faster binary for headless CI, which never needs multi-agent coordination or a UI server. `c10` builds+releases BOTH variants per platform as distinct release assets.
- [ ] **Exit-code taxonomy distinguishes "target project failed a check" from "the enforcer itself is broken."** A rule violation / T1 hard-fail is one exit-code class; an internal panic, decode error, or unexpected crash in the engine is a DIFFERENT exit-code class (never silently coerced into a generic non-zero that a consumer's CI would misread as "my code is bad"). Every panic is caught at the top of `main` (no bare unhandled panic escaping to an ambiguous OS-level abort) and reported through the internal-error class with a diagnostic pointing at the enforcer itself, not the scanned project.
- [ ] **CI mode is FULLY mechanical — zero AI in the loop.** No subcommand's pass/fail path may depend on an MCP round-trip, an agent interpreting output, or any judgment call; the binary's own exit code is the entire verdict for a headless CI runner with no Codex/Claude present.
- [ ] `enforcer serve` (or stdio-detected) starts the `enforcer-mcp` server on stdio — one binary = MCP server + CLI.
- [ ] Produce the `enforcer` binary target; wire config via `enforcer-config` (the single declarative control-plane both surfaces read), output via `enforcer-domain` `Report` rendering.
- [ ] `cargo test -p enforcer-cli` passes with fail/pass fixtures: `enforcer check` on a fixture tree exits non-zero with findings (fail fixture) and zero on a clean tree (pass fixture); each of the three scope modes parses and routes; a `--base/--head` + `<paths...>` collision is a clap error; there is no flag that suppresses a finding; `serve` starts the MCP loop.
- [ ] Clean `cargo clippy` / `cargo fmt --check` (deny wall honored everywhere except the single output-sink module; no `pub use` barrels).

### Orphaned CLI subcommands to reconcile into the clap grammar (WAVE 4 gap — present in `src/cli-command-dispatch.mjs`, absent from arc-22's grammar)
The retired Node dispatcher (`src/cli-command-dispatch.mjs` `COMMAND_HANDLERS`/`RAW_COMMAND_HANDLERS`) shipped four subcommands the Rust clap grammar above never enumerates. They MUST be ported as first-class clap subcommands (or explicitly retired with a routed decision row), or the Rust CLI silently drops surface the Node CLI had.

- [ ] **`verify` subcommand + the four verify modes.** Port `verify` (Node `handleVerifyCommand` → `runEnforcerVerify`). The `--mode` flag is validated against `VERIFY_MODE_CHECKS = { fast, local, ci, parent }` (`scripts/rust-rules-scan-core-args-options.mjs:3`, `normalizeVerifyMode`), DEFAULTS to `local`, empty string coerces to `local`, and any other value is a hard parse error (`Unknown verify mode: <value>`). clap must reproduce exactly: an enum of `{fast, local, ci, parent}` with `default = local`, unknown values rejected at parse time (clap error, non-zero, not a generic finding exit code). **d06-vocabulary reconciliation (MUST resolve, do not let the two vocabularies collide):** d06 owns the lifecycle verbs `plan|implement|check|fix|review` in `src/lifecycle.rs`; `verify` and its modes are a SEPARATE, orthogonal axis — `verify` is a scope/aggregation profile over checks (fast=quick local subset, local=default dev, ci=headless mechanical, parent=OcentraParent-parity superset), NOT a lifecycle phase. State the composition explicitly in the grammar: the d06 `check` verb and `verify` MUST NOT be aliases of each other; `verify --mode <m>` composes with the tri-modal scope grammar (`<paths...>` | `--base/--head` | `--all`) the same way `check` does; the d06 `review` verb is likewise distinct from `verify --mode parent`. Document that `verify` is retained as a distinct top-level subcommand (not folded into d06's family) so no existing `enforcer verify --mode ci` invocation breaks.
- [ ] **`advise` subcommand.** Port `advise` (Node `handleAdviseCommand`). Today it accepts exactly one target, `literals`, and routes to the `literal-risk` check (`handleCheckCommand` with `checkName: "literal-risk"`); any other `adviseTarget` is a hard error (`advise currently supports only literals`). The literal-risk semantics live in **arc-13** (literal-scan registry / LIT-1) — `advise` is the CLI seam onto that engine; wire the clap `advise literals` subcommand to the arc-13 literal-risk path, preserving the single-target constraint (unknown advise target = parse/usage error, not a silent no-op).
- [ ] **`architecture` subcommand + its named checks.** Port `architecture` (Node `handleArchitectureCommand` → `runArchitectureCli`, `src/cli-checks.mjs:168`). Grammar: `architecture check --language <lang> --scope <files|diff|all>` — a bare `architecture` with no `check` token is a usage error. It routes to the `architecture-policy` named check (`src/cli-checks.mjs:183`, `runEnforcerCheck` `checkName: "architecture-policy"`). Both named checks in the family MUST be reachable and survive the port: **`architecture-policy`** and **`import-boundaries`** (registered in `src/checks.mjs:151`/`:318`). These are the same named-check surface arc-15/d01's check-enum parity row tracks; arc-22 only owns the CLI routing seam onto them.
- [ ] **`ledger` alias of `coordination` (the alias MUST survive the port).** Node maps BOTH `coordination` and `ledger` to the identical handler (`RAW_COMMAND_HANDLERS.coordination === RAW_COMMAND_HANDLERS.ledger === handleCoordinationCommand`, `src/cli-command-dispatch.mjs:63-64`). The Rust clap grammar MUST register `ledger` as a visible alias of the `coordination` subcommand (clap `alias`/`visible_alias`), dispatching to the exact same handler and arg grammar — an `enforcer ledger <args>` invocation must be byte-for-byte equivalent to `enforcer coordination <args>`. (Note: under the lite/full split, both names live behind the `full` feature and BOTH must be compiled out together in `lite`/`ci` — the alias must not leak a dangling name in the lite binary.)

### Fixture intent for the four orphaned subcommands (each: subcommand parses + routes + exit code)
- [ ] `verify` fixtures: (pass) `enforcer verify --all` on a clean tree parses, routes to the verify engine, exits 0; (fail) `enforcer verify --all` on a dirty fixture tree exits non-zero with findings; (mode-default) `enforcer verify` with no `--mode` resolves to `local`; (mode-parse-fail) `enforcer verify --mode bogus` is a clap error with a distinct exit-code class (internal/usage), NOT a finding exit code; each of `--mode {fast,local,ci,parent}` parses and routes.
- [ ] `advise` fixtures: (pass/fail) `enforcer advise literals` parses and routes to the arc-13 literal-risk check, exiting non-zero when the fixture contains a flagged literal and zero when clean; (usage-fail) `enforcer advise <other>` is a usage error (single-target constraint preserved).
- [ ] `architecture` fixtures: (pass) `architecture check --language rust --scope all` on a compliant fixture exits 0; (fail) same on a fixture that violates `architecture-policy`/`import-boundaries` exits non-zero with the corresponding findings; (usage-fail) bare `architecture` (missing `check`) is a usage error; both named checks are individually exercised.
- [ ] `ledger` alias fixture: `enforcer ledger <args>` parses to the SAME handler and produces output identical to `enforcer coordination <args>` (assert alias equivalence, not merely that it parses); and a fixture asserting the alias is compiled OUT alongside `coordination` in the `lite`/`ci` build.
