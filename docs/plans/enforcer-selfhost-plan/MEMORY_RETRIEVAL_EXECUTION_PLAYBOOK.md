## 0. Roles

- **Orchestrator** (one session, capable model): reads doctrine, sequences subpacks, writes worker prompts, coordinates lanes. NEVER writes product code.
- **Gatekeeper** (same seat as orchestrator): zero-trust verifies every lane before integration. The two hats are one session; the discipline is that gatekeeping is mechanical (checklist §5), not judgment-of-trust.
- **Workers** (cheaper models, isolated worktrees): implement exactly one subpack or doc task on a `lane/x06-*` branch. Sonnet-class for crates, haiku-class for docs/fixtures. Workers read, write, edit, test; they self-report but are never believed without verification.

## 1. Canonical read order (for ANY executor entering cold)

1. `MEMORY_RETRIEVAL_OWNER_INTENT.md` — binding vision; outranks everything; fake green = failure.
2. `MEMORY_RETRIEVAL_DESIGN_INPUTS.md` — the 10 sources and what to borrow.
3. `MEMORY_RETRIEVAL_BORROW_POLICY.md` — HOW to borrow: inspiration, never transplantation.
4. `refs/x06-source-scout-digests.md` — what the sources actually contain (verified 2026-07-04); replaces most research passes.
5. `MEMORY_RETRIEVAL_DECISIONS.md` — locked choices; never re-litigate, report evidence instead.
6. `MEMORY_RETRIEVAL_QA_PROOF_GATE.md` — the REQUIRED 100-row gate; then `MEMORY_RETRIEVAL_QA_BENCHMARKS.md` (QA-250 + longitudinal §3).
7. `MEMORY_RETRIEVAL_KG_RAG_MASTER_PLAN.md` → `MEMORY_RETRIEVAL_IMPLEMENTATION_PACKS.md` (your one subpack) → `MEMORY_RETRIEVAL_PARITY_HARNESS.md` → `MEMORY_RETRIEVAL_TEST_MATRIX.md`.
8. `MEMORY_RETRIEVAL_STATE_BOARD.md` — where the program currently stands; RESUME from there.
9. `workpacks/x06-harness-memory-graph.md` — owns globs and acceptance.

## 2. Subpack sequence and lane naming

X06.1 store → X06.2 code-KG indexer → X06.3 graph algorithms → X06.4 fulltext/vector/rerank → X06.5 weaver → X06.6 continuous learning → X06.7 MCP/CLI/watch/diagnostics → X06.8 federation → X06.9 parity/benchmark harness. Doc lanes (QA authoring, digests) run in parallel any time.

Lanes: `lane/x06-<n>-<name>` (e.g. `lane/x06-2-codegraph`), branched from `origin/rust-build`, pushed to origin. Parallelism rule: two subpacks may run concurrently only if their owns-files are disjoint (the pack table §1 defines ownership); a needed-but-unowned surface is consumed through a trait seam, wired at integration.

## 3. Worker prompt template (every x06 worker prompt contains ALL of this)

```text
1  ROLE line: which subpack, which model tier, self-report model in final message.
2  STEP 0: git fetch origin && git checkout -B lane/x06-<n>-<name> origin/rust-build (isolated worktree).
3  READ ORDER: playbook §1 items 1–6 + YOUR subpack section + state board.
4  EXACT FILE CLAIMS: ≤10 paths/globs from the pack table. Everything else is untouchable;
   name the specific files of ADJACENT subpacks as explicit do-not-touch.
5  SCOPE: the subpack's hard requirements + hard tests, verbatim from IMPLEMENTATION_PACKS,
   plus any DECISIONS entries that constrain it.
6  BORROW TERMS: which sources it may consult (per BORROW_POLICY posture), ONE research pass max, then build.
7  GATES (before every push): cargo build --workspace && cargo test -p enforcer-memory
   && cargo clippy --workspace --all-targets -- -D warnings && cargo fmt --check.
   Zero #[allow(clippy::…)]. Never delete a test to go green.
8  CHECKPOINT: push at first green, then increments.
9  MEMORY DUTY: append NDJSON to memory/streams/lane-x06-<n>-<name>.ndjson
   per memory/schema/memory-record.schema.json.
10 FIXTURES: new fixture extensions pinned eol=lf in .gitattributes in the same commit.
11 PROTECTED: never modify (owner-set lines; never mint (owner-set markers (D-13).
12 FINAL MESSAGE: lane + head SHA, files touched, tests added, PASTED gate output,
   harvested-from provenance, deviations, self-reported model.
```

## 4. Proof duty per subpack

A subpack is DONE only when its proof artifact exists and is honest: `proof/memory/x06-<area>.json` per the pack table and TEST_MATRIX prefixes. A proof artifact generated by a test that would pass on an empty implementation is fake green. The QA gate (100 rows → `x06-rag-qa.json`) and feature-parity rollup close the whole workpack, not any single subpack.

## 5. Gatekeeper checklist (mechanical — run ALL of it on every lane before cherry-pick)

- [ ] `git fetch` + diff `origin/rust-build...origin/lane/…`: every touched file inside the lane's claims; Cargo.lock/Cargo.toml changes explainable.
- [ ] Owner-set scan: diff shows zero REMOVED and zero ADDED `(owner-set` lines (additions are owner-only, D-13/L41).
- [ ] Mechanical recount of every countable claim (test counts, row counts, category sums) — script, never the worker's report (L41).
- [ ] Independent gate rerun in a clean checkout of the lane: build --workspace, test -p changed crates, clippy -D warnings, fmt --check (L36 scope).
- [ ] No deleted/weakened tests; new tests actually assert behavior (spot-read the asserts; L37 vacuous-verify pattern).
- [ ] Borrow hygiene per BORROW_POLICY §4 (provenance trailers, no verbatim lifts, no unapproved deps).
- [ ] Proof artifact (if claimed) opens, parses, and its content matches the tests that ran.
- [ ] Integration: cherry-pick to rust-build (scoped adds only — shared tree, L40), rerun workspace build, push immediately, update STATE_BOARD in the same push.

## 6. Failure and salvage

- Worker reports failure honestly → orchestrator triages: respec, respawn, or descope with owner.
- Lane dead with no checkpoint >40min → salvage triage (L38): finished crate → integrate directly; partial → fresh worker ADOPTS the worktree files; stub → discard, rebuild.
- Verification failure → fix-pass message to the SAME worker with computed, exact defect lists (never "recheck your work"); one fix pass, then replace the worker.
- Every incident banks a lesson: `refs/orchestration-lessons.md` (append-only L-row) + a memory-stream record.

## 7. Quality doctrine (what "focus on quality" means here)

- The fake-green definition (OWNER_INTENT) is the acceptance test for every claim of progress.
- Metrics are recorded per-row, per-run, into proof artifacts; a number in a chat message does not exist.
- Regressions ratchet: longitudinal reruns that score below the previous recorded run FAIL (QA_BENCHMARKS §3).
- When speed and the gates conflict, the gates win. When a checklist and the owner vision conflict, the vision wins and the checklist gets fixed (OWNER_INTENT protection clause).
